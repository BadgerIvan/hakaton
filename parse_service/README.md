# Универсальный локальный парсер, версия 2

Обновление приложения из cft_rag_corpus. Скопируйте `app/`, `requirements.txt` и `tests/` в корень существующего проекта. Папки `raw/`, `parsed/`, `rag/` и `registry/` с данными в этом архиве не поставляются и при установке не заменяются. Исходники никогда не перемещаются и не изменяются.

## Установка и запуск

Python 3.10+:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m app --raw ./raw --out ./parsed --force
```

Для первого сравнения с прежней версией лучше использовать отдельную папку:

```bash
python -m app --raw ./raw --out ./parsed_v2
```

`--raw` может указывать на любую папку. Распределять файлы по расширениям необязательно: `raw/other/`, вложенные папки и файлы без расширений обрабатываются тем же механизмом определения формата.

Дополнительные системные инструменты для Debian/Ubuntu:

```bash
sudo apt install tesseract-ocr tesseract-ocr-rus tesseract-ocr-eng antiword
```

Для старых PPT и альтернативной конвертации DOC:

```bash
sudo apt install libreoffice
```

Эти программы необязательны для остальных форматов. Если нужного инструмента нет, причина попадает в отчёт по конкретному файлу. Устанавливать LibreOffice ради HTML/PDF/DOCX не нужно. Парсер не скачивает сайты и не выполняет скрипты или макросы документов.

## Форматы и инструменты

| Данные | Извлечение |
| --- | --- |
| TXT, MD, неизвестные текстовые расширения, текст без расширения | Чтение текста, charset-normalizer для кодировки |
| HTML, HTM, XHTML | BeautifulSoup + markdownify; заголовки, списки, таблицы, очистка меню и служебных блоков |
| PDF | PyMuPDF; текст по страницам; для страниц без текста попытка OCR |
| PNG, JPEG, TIFF, BMP, GIF, WebP | Pillow + системный Tesseract, языки rus/eng при наличии |
| DOCX | python-docx: абзацы, заголовки и таблицы |
| DOC | antiword; при его отсутствии — LibreOffice в DOCX |
| XLSX, XLSM | openpyxl; листы и таблицы; формулы сохраняются как текст, не вычисляются |
| XLS | xlrd |
| PPTX | python-pptx: текст, таблицы, группы фигур, заметки по слайдам |
| PPT | LibreOffice в PPTX, далее python-pptx |
| ODT, ODS | ZIP + lxml: content.xml, абзацы, заголовки и таблицы |
| RTF | striprtf |
| CSV, TSV | csv: определение разделителя, Markdown-таблицы |
| JSON | Стандартный json; специальный адаптер ЦФТ при catalog_kind в метаданных, иначе универсальный обход структуры |
| JSONL, NDJSON | Построчное чтение json |
| YAML, YML | yaml.safe_load_all, структура в Markdown |
| XML, SVG | lxml с отключёнными внешними сущностями и сетью; структура и текст, не визуальная отрисовка SVG |
| CSS, JS, TS, PY, SQL, LOG, INI, CFG, TOML, RST | Текст в блоке кода; не исполняется |
| ZIP, TAR, TAR.GZ, TGZ, GZ | zipfile/tarfile/gzip; документы внутри проходят через те же парсеры |
| EPUB | ZIP + XML: чтение порядка глав spine, затем HTML-парсер |

OCR не описывает фотографии, схемы и графики — извлекается только распознанный текст. Векторные фигуры и изображения на слайдах не распознаются. Форматирование сложных PDF, сложные объединения ячеек и формулы ODS могут требовать проверки. Для DOC/PPT без соответствующего системного конвертера полноценная обработка недоступна.

Поддержку любого произвольного бинарного формата обещать нельзя: аудио, видео, EXE, RAR/7z и зашифрованные документы требуют отдельных средств. Здесь неизвестный бинарный файл получает явный статус unsupported; читаемый неизвестный файл обрабатывается как текст. Парсер определяет PDF, Office, ZIP и изображения по содержимому, даже если они лежат в other/ или имеют неверное расширение. Для неоднозначного контейнера старого Office может потребоваться правильное расширение.

## Результат и отчёт

Все успешные документы получают единый результат Markdown с YAML-шапкой: source, source_format, original_extension, parser, parser_version, sha256, metadata_sha256, warnings и метаданные источника. Файл `name.pdf` превращается в `name.pdf.md`, чтобы `name.txt` не перезаписывал его. При миграции старый `name.md` удаляется только после успешной записи нового и только если в его YAML указан тот же исходник.

Отчёты создаются в `registry/` рядом с папкой результата:

- `parsing_report.jsonl`: одна запись на каждый входной документ, путь результата, парсер, статус, предупреждения или причина пропуска;
- `parsing_summary.json`: общее число файлов, количество игнорируемых метаданных и счётчики статусов.

Статусы: written — создан Markdown; unchanged — документ и настройки уже обработаны; excluded — явное include_in_rag=false; unsupported — неизвестный бинарный формат; error — ошибка чтения/конвертации либо отсутствующая зависимость.

Соседние `.meta.json` — настройки, а не документы. Сохраняется совместимость с прежними sidecar-файлами. Если `include_in_rag` равно false, документ не конвертируется. Поэтому CSS из прежнего корпуса по-прежнему исключены: именно такая настройка была при сборе. Новый CSS без этого ограничения будет разобран. Не снимайте исключения со всех файлов автоматически.

Один архив создаёт один составной Markdown с именами внутренних файлов; причины пропуска отдельных членов записываются в warnings. Вложенные архивы не раскрываются автоматически. Не индексируйте одновременно составной текст ZIP и отдельные документы, уже извлечённые из того же ZIP: появятся повторы.

Ограничения: входной файл до 128 MiB, архив до 500 файлов и до 128 MiB распакованных данных; вложенные архивы, опасные пути и зашифрованные ZIP-члены пропускаются. Ограничение OCR: 100 кадров и 40 мегапикселей на кадр. Тайм-аут внешних конвертеров — 90–120 секунд на вызов. Это базовые ограничения; для недоверенных документов запускайте обработку в отдельном контейнере с ограничением памяти.

После замены парсеров выполните --force. Ранее обработанные файлы без изменений при следующем запуске пропускаются. Старые результаты удалённых исходников автоматически не чистятся: для чистого пересоздания используйте новую папку --out. Отчёт отражает текущие входы, а не число исторически накопленных Markdown-файлов.

Утилиты построения rag/chunks.jsonl из прежнего корпуса не входят в это обновление. После проверки parsed используйте существующий tools/build_rag.py. Его фильтрация коротких текстов и дедупликация — отдельный этап, поэтому число документов в RAG может снова отличаться от числа результатов парсинга.

## Откуда взялись разные количества в прежнем корпусе

Проверено по исходному снимку:

- raw содержит 394 файла: 197 документов/ресурсов + 197 соседних файлов .meta.json;
- старая версия: 185 Markdown, 5 исключённых входов, 7 неподдерживаемых входов;
- 7 неподдерживаемых — 4 CSS и 3 ZIP; CSS проверялись по расширению до чтения include_in_rag=false;
- 5 исключённых — меню каталога JSON, скан политики обработки данных и три robots.txt;
- из 185 Markdown в RAG включены 184: одна короткая страница регистрации отложена;
- 881 — число фрагментов 184 документов, а не число исходников;
- PDF/DOCX, извлечённые из ZIP, уже лежат в raw отдельно от архивов, поэтому это не независимые новые источники;
- новая версия на тех же входах: 188 Markdown, 9 исключённых, 0 unsupported, 0 ошибок. Разница +3 — составные тексты ZIP. CSS корректно попали в excluded по их метаданным.

## Проверки

```bash
python -m unittest discover -s tests -v
```

Автоматические проверки охватывают неизвестные расширения, подписи файлов, коллизии имён, JSON/JSONL, CSV, YAML, XML, CSS, RTF, XLSX, PPTX, ZIP/GZIP, ODT/EPUB, инкрементальную обработку и отчёты. OCR-тест запускается при наличии Tesseract. Полный корпус также проверен отдельно; результаты в verification_report/.
